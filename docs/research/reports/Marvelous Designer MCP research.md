# Draft outside MD, then verify every seam

Nothing in this research gives md-mcp a per-piece 3D transform, a seam-removal call or a readable error channel in Marvelous Designer 2026.0.315, and none of the ten other MD and CLO3D MCP servers has found one either. The leverage lies on either side of MD. Upstream, a garment should be drafted from pattern-making rules (a cape is an annular sector whose neck radius is the neckline divided by 2π times the circle fraction) or generated by GarmentCode, whose explicit stitch list maps almost directly onto MD's pattern JSON, so that every seam exists in a checked plan before it exists in MD. Downstream, three things make each mutation checkable: a seam ledger decoded from `ExportPatternJSON` (another server has already built one against this exact build), a tiled snapshot sheet, and a `.zprj` checkpoint as the only available rollback. MD's own GUI places the shell with arrangement points and then seats collars, facings and linings with Superimpose and Smart Arrangement. The API reaches the first step and none of the second. Layer Clone always sews every edge, professionals strip those seams by hand, and the API cannot, so a lining built over the bridge has to be drafted as separate pieces sewn deliberately. Three findings challenge the repo's measured claims and should be settled first. MD's own documentation numbers `SetCamViewPoint`'s back view 8, but `md_snapshot` accepts only 0–7. `SetArrangementPosition` takes four integers whose units are probably bounding-volume coordinates, not millimetres. And a `SetTimer`-based listener has reportedly served MD 2026.0.315 without the never-ending Run that AGENTS.md calls mandatory. **Nothing here was measured against a running MD.** The API claims come from documentation, other people's code and a read-only scan of the installed binary's strings, so every API-level conclusion is a hypothesis until the measurements listed at the end are run with MD open.

## MD places by volume, seats by sewing, and reports errors only on screen

### The GUI's placement model starts at the avatar, not the garment

MD's placement model is coarse first, then fine. Each avatar carries **bounding volumes**: cylinders or cuboids spanned between two joints. **Arrangement points** sit on those volumes. Clicking a point puts the centre of the selected pattern on it and wraps the pattern round the volume's curve ([MD help](https://support.marvelousdesigner.com/hc/en-us/articles/47358262924185-Arrange-Pattern-with-Arrangement-Points-Flip-Wrap-Direction)). Everything after that is fine-tuning in Property Editor ▶ Arrangement. There, Position X and Position Y move the piece "according to the arrangement bounding volume", and Offset "adjusts the offset and curvature between the arrangement bounding volume and the pattern" ([MD help](https://support.marvelousdesigner.com/hc/en-us/articles/47358278939417-Arrangement-Property-Setting)).

When the points are wrong, MD's answer is to fix the avatar, not the garment. Avatar Editor ▶ Arrangement edits each volume's start and end joints, height and radii, and each point's volume, X, Y, offset and wrap direction, then saves them as `.pan`, `.arr` and `.avt` files for reuse ([Avatar Editor](https://support.marvelousdesigner.com/hc/en-us/articles/47358128221337-Avatar-Editor-ver-2025-0)). Points generated on OBJ import work "only when imported OBJ is either in T or A pose" ([MD help](https://support.marvelousdesigner.com/hc/en-us/articles/47358223288601)). MD support says points are not converted automatically on import ([MD community](https://support.marvelousdesigner.com/hc/en-us/community/posts/48269284495641-Arragement-Points-Automatic-Generation-Feature-Request)), and a moderator describes the automation as built for bipeds, with anything else left to manual editing ([MD community](https://support.marvelousdesigner.com/hc/en-us/community/posts/48283176857753-Reset-3D-Arrangement-problem)). Nardo's tail is exactly that case: md-mcp measured `Body_Back_Center_1` putting a piece a metre behind the back ([md-conventions](../../md-conventions.md)). It follows that the GUI-faithful fix is a one-off human edit of Nardo's torso volumes, saved with the avatar, which every later garment then benefits from.

Secondary pieces are never placed from points:

- **Superimpose (Over/Under/Side)** arranges "a newly sewn Pattern onto its corresponding Pattern" and is "helpful when arranging facings, linings, cuffs, collars", but only for pieces already sewn ([Superimpose](https://support.marvelousdesigner.com/hc/en-us/articles/47358389619481-Superimpose)). CLO staff use Side to put a rib "next to the sewing line" of a simulated shell ([CLO community](https://support.clo3d.com/hc/en-us/community/posts/4409649041689-Superimpose-and-Sublayer-what-the-difference-Plus-question-about-Puckering)).
- **Smart Arrangement** places a newly sewn piece "to where it is sewn as draped" ([Smart Arrangement](https://support.marvelousdesigner.com/hc/en-us/articles/47358423599257-Smart-Arrangement)).
- **Fold Arrangement** pre-folds "Seam Allowances, collars and cuffs before activating the Simulation for better stability" ([Fold Arrangement](https://support.marvelousdesigner.com/hc/en-us/articles/47358260153881-Fold-Arrangement)).
- **Free placement** uses the gizmo or Direct Positioning with simulation off ([Gizmo](https://support.marvelousdesigner.com/hc/en-us/articles/47358192192665-Move-Rotate-Pattern-with-Gizmo); [Direct Positioning](https://support.marvelousdesigner.com/hc/en-us/articles/47358256542361-Direct-Positioning)).
- **Re-drape 3D Arrangement** needs a Fitting Suit on the avatar ([Auto Fitting](https://support.marvelousdesigner.com/hc/en-us/articles/47358335130649-Auto-Fitting)). CLO says it supports only CLO avatars and custom avatars that have one ([CLO support](https://support.clo3d.com/hc/en-us/articles/360034333873-Re-drape-3D-Arrangement-ver-5-1)).
- **Auto 3D Arrangement** is CLO's: it places pieces from learned data ([CLO support](https://support.clo3d.com/hc/en-us/articles/13200837772185-Auto-3D-Arrangement-ver-7-1)). MD 2026.0.315's binary contains the same dialog and a 139 MB `Auto_Arrangement_Model_2_1_0.eom`, but MD has no help page for it, so it is unknown whether MD's menus offer it ([binary scan](<../research_notes/Marvelous Designer MCP research/md_python_api_surface.md>)).

Professionals use the draping aids as temporary steps and take each one away afterwards:

- **Freeze before Deactivate.** Frozen patterns collide; deactivated ones do not. MD's advice is "draping and freezing inner Garments first, then draping outerwear" ([Freeze/Unfreeze](https://support.marvelousdesigner.com/hc/en-us/articles/47358315135897-Freeze-Unfreeze)).
- **Layer.** The Layer value pushes a piece outward. Once the order is right, set it "back to zero ('0') for more stable simulation" ([Use Layer](https://support.marvelousdesigner.com/hc/en-us/articles/47358288780441-Use-Layer-Drape-Additional-Garment)).
- **Shrinkage** temporarily draws an inner layer against the avatar ([Shrink Pattern](https://support.marvelousdesigner.com/hc/en-us/articles/47358324821785-Shrink-Pattern)).
- **Particle distance** is 20 mm while building and under 5 mm for the finished garment ([Particle Distance](https://support.marvelousdesigner.com/hc/en-us/articles/47358268602777-Particle-Distance-Setting)).
- **History ▶ 3D State** is the GUI's checkpoint ([History Window](https://support.marvelousdesigner.com/hc/en-us/articles/47358269290393-History-Window)).

CLO staff's shell-and-lining recipe combines these: simulate the lining and deactivate it; simulate the shell on layer 1 and deactivate it; reactivate and freeze the lining; simulate the shell over it; unfreeze; return the shell to layer 0 ([CLO community](https://support.clo3d.com/hc/en-us/community/posts/4409649041689-Superimpose-and-Sublayer-what-the-difference-Plus-question-about-Puckering)). The cape session's freeze, pull, unfreeze and lengthen loop used Freeze to hold a deliberately short piece, which no source uses it for ([session report](../../sessions/2026-10-11-vampire-cape.md)).

The API covers the first of these steps and almost none of the rest. The table maps each GUI tool to what the documentation and binary scan suggest is bound in 2026.0.315. "Measured" means md-mcp has measured it; everything else is unmeasured.

The consequence is structural. md-mcp can arrange a shell coarsely, but it can never seat a collar, facing or lining against its neighbour the way the GUI does. A garment built over the bridge therefore has to reach simulation already in a configuration that sewing and gravity alone will resolve. That shifts onto the 2D draft and the seam plan the work that Superimpose does in the GUI.

### The documentation stops at 2025.1 and the build exposes more than it says

MD's Python API is documented as "Marvelous Designer API 0.1" ([MD docs](https://developer.marvelousdesigner.com/)). Its changelog covers only 2024.2.189 to 2025.1.201, with no 2026 entry and nothing marked removed ([MD changelog](https://developer.marvelousdesigner.com/changelog.html)). The entries that matter here:

- 2025.1.157 fixed `MovePatternPoint` moving other selected points.
- 2025.1.107 added `.py` plug-ins in Plug-in Manager and `AlignAvatarsAndGarmentToCenter`.
- 2025.0.157 added the animation-recording calls.

The docs still send users to "Main Menu → Script → Python" ([python.rst](https://developer.marvelousdesigner.com/_sources/python.rst.txt)), a menu this build does not have ([md-conventions](../../md-conventions.md)). The only official samples are four short "API Scenario" snippets, for animation, simulation, pattern creation and Substance import ([scenario.rst](https://developer.marvelousdesigner.com/_sources/scenario.rst.txt)). No official sample repository was found. The API itself arrived with the Linux edition in October 2025 and is sold only on an Enterprise plan with floating licences at **US$2,300 a year** ([CG Channel](https://www.cgchannel.com/2025/10/marvelous-designer-is-now-available-for-linux/)). Coverage of 2026.0 and 2026.1 mentions no API changes at all ([CG Channel](https://www.cgchannel.com/2026/08/clo-virtual-fashion-releases-marvelous-designer-2026-1/)). 2026.1 adds an experimental Seamline Rip and a Variable Fold Angle, both GUI features and neither in 2026.0.315 ([Seamline Rip](https://support.marvelousdesigner.com/hc/en-us/articles/59816167297433-Seamline-Rip); [Variable Fold Angle](https://support.marvelousdesigner.com/hc/en-us/articles/59783425428121-Internal-Line-Variable-Fold-Angle)).

CLO's documentation is the better reference for what calls mean. It carries the same docstrings, documents **822 names to MD's 509**, and contains every MD name ([CLO API list](https://developer.clo3d.com/list.html)). Its changelog also shows the shared API changing. CLO V10.0.3 (July 2026) removed `ReDrape3DArrangement`. CLO V11.0.0 (August 2026) restored it and added:

- `MergeSewnPatterns` and `GetPatternOnBodyDetails`;
- outline and line geometry getters;
- material property setters;
- seam-line IDs in `ExportPatternJSON`, "so seam line pairings can be fully reconstructed";
- API warnings routed to the Python editor;
- removal of "direct MessageBox calls from CloApi error paths", which had been hanging scripts.

All of this is from the [CLO changelog](https://developer.clo3d.com/changelog.html). **None of the V11 additions appears in MD 2026.0.315's strings** ([binary scan](<../research_notes/Marvelous Designer MCP research/md_python_api_surface.md>)), so MD's API sits between its own docs and CLO V11.

The binary scan read the `__FUNCSIG__` and pybind11 wrapper strings from the 194 MB executable. It found 739 C++ members across seven API classes. Many are compiled in but have no Python binding, among them `ChangeFabricWithJson`, `ExportStdViewImage`, `ExportGLTF`, `ImportDXF`, the nesting calls, the strain-map toggles and the colourway family ([binary scan](<../research_notes/Marvelous Designer MCP research/md_python_api_surface.md>)).

More useful are the calls that appear to be bound but that md-mcp has never measured ([MD API list](https://developer.marvelousdesigner.com/_sources/list.rst.txt); [CLO API list](https://developer.clo3d.com/list.html); [binary scan](<../research_notes/Marvelous Designer MCP research/md_python_api_surface.md>)):

- `ReDrape3DArrangement`
- `GetAllStitchProperty`: every stitch in the scene, as JSON
- `GetLinkedPatternLists`: linked groups, "e.g., Layer Clone", as JSON
- `GetGraphicStylePosition(graphic, False)`: positions "based on the 3D window", according to CLO
- `GetBoundingBoxOfPattern`: size, not position
- `GetCustomViewInformation`: camera matrix and field of view
- `ExportFabric` to `.jfab`, with `AddFabric` reading `.jfab` back
- `CombineZfab`
- `SetUseSameColorAsFront`

The scan also found lower-case `rest_api` and `sample_api` module strings, the second behind an authorisation check. `REST_API` itself is documented as an outbound HTTP client (`CallRESTPut`, `CallbackRestRequest`), not a server ([MD API list](https://developer.marvelousdesigner.com/list.html)). The scan's way of deciding that a call is bound was checked against DXF only. `md_api` on a live MD is the ground truth.

### MD's errors live in dialogs, and nothing writes them down

No bound name reads an error, a log, a message or an undo history. The only message call is the modal `DisplayMessageBox` ([binary scan](<../research_notes/Marvelous Designer MCP research/md_python_api_surface.md>)). The errors the documentation mentions are return values, such as an empty string from `ExportZPrj` ([MD API list](https://developer.marvelousdesigner.com/_sources/list.rst.txt)). The meshing error from the cape session is a UI string: in full, "Pattern Boundary is intersected while meshing. Please decrease the particle distance." It sits beside "Overlapping Sewing Line", "There are some abnormal seamlines in the file (marked as red)" and "Arrangement Points were not fitted to the avatar" ([binary scan](<../research_notes/Marvelous Designer MCP research/md_python_api_surface.md>)). The only text logs MD has written on this machine are `api_plugin_log.txt`, which records plug-in registration, and `authlog.txt`. Headless command-line strings, `headlesslog` among them, exist in the binary. But an MD support reply, seen only as a search-result summary, says there is no headless MD session ([MD support](https://support.marvelousdesigner.com/hc/ko/community/posts/48273620823705/comments/48273605186969)).

The consequence for P0.2 is plain: there is no file to tail and no call to poll. MD's messages can reach the caller only in two ways: by reading MD's windows from outside the process, or by inferring trouble from scene state (mesh counts, seam counts, piece positions) after each call. The meshing message also names its own remedy, which points at the cause: a degenerate outline left by a flung point.

## Professionals strip Layer Clone's seams and draft linings as separate pieces

Layer Clone does exactly what the cape session saw. MD documents it as creating an instance "while sewing its Pattern outlines and Internal Lines to its instance's Pattern outlines and Internal Lines", meant for "padded jackets, collars, cuffs and other garments/details made with multiple layers" ([Layer Clone](https://support.marvelousdesigner.com/hc/en-us/articles/47358338558745-Layer-Clone)). CLO adds that linked editing is applied ([CLO help](https://support.clo3d.com/hc/en-us/articles/115012378408-Layer-Clone-Over)), and CLO staff confirm that the seams are set to Turned ([CLO community](https://support.clo3d.com/hc/en-us/community/posts/18397722150809-Have-big-gap-when-use-Layer-Clone-Over)). That matches md-mcp's measurement: `bIsTurned: true` and a 180° fold on every outline line ([session report](../../sessions/2026-10-11-vampire-cape.md)). The same CLO specialist explains why a cloned layer never joins smoothly: it is sewn to the layer beneath, where a whole separate inner layer would not be ([CLO community](https://support.clo3d.com/hc/en-us/community/posts/18397722150809-Have-big-gap-when-use-Layer-Clone-Over)). MD 2026.0.315 has no "Clone as Lining" command and no option to clone without sewing ([GUI research note](<../research_notes/Marvelous Designer MCP research/md_workflow_placement_layers.md>)).

Practitioners treat the automatic seams as scaffolding to be taken down. In a CLO thread on bag linings ([CLO community](https://support.clo3d.com/hc/en-us/community/posts/900002294926-Lining-and-facing-questions-on-bag)):

- One member writes that "only the rim sewing lines should be retained the rest need to be renewed or edited".
- Another builds the shell, layer-clones it under, removes linked editing, deletes the seams and "sew[s] the lining again just as it should be: independent of the outer shell".
- CLO's official answer: sew the lining to the shell temporarily, Superimpose Under, then undo the temporary sewing and sew the lining to itself.

The sources disagree only about identical pieces. A CLO staff member said in 2021 that clone-under is fine when lining and shell are "the exact same pattern piece" ([CLO community](https://support.clo3d.com/hc/en-us/community/posts/4409649041689-Superimpose-and-Sublayer-what-the-difference-Plus-question-about-Puckering)). Even then the clone bonds the lining to the shell at the shoulders, which the cape construction sources forbid (see the next section). Where lining does meet shell, MD advises setting Fold Strength to 0 so the sewn boundary stops inflating ([Seamline Property](https://support.marvelousdesigner.com/hc/en-us/articles/47358171818521-Seamline-Property-ver-2025-0)).

The API has no seam removal, so the only lining md-mcp can build today is one drafted as its own pieces and sewn deliberately: lining to lining at the shoulders, and to the shell only at the bagged edges. Practitioners also use a cheaper third option when "4 layers of fabric is difficult to simulate": a single layer whose back face carries a different material ([CLO community](https://support.clo3d.com/hc/en-us/community/posts/360033634853-Sewing-Arranging-facing-for-lapel); [MD help](https://support.marvelousdesigner.com/hc/en-us/articles/47358373247257-Fabric-Front-Back-Side-Setting)). Whether md-mcp can write that back face safely is an open P4 measurement.

Collars and facings depend on fold lines, interlining and temporary strength:

- **Fold lines.** An internal line's Fold Angle runs from 0° to 360°, where 180° means flat, and Fold Strength runs from 0 to 20 ([Fold Pattern](https://support.marvelousdesigner.com/hc/en-us/articles/47358354961049-Fold-Pattern)). A community answer about collars that all stand up puts it bluntly: "Default is 180 ... You have to change it to nearly 0 to have it fold at all" ([MD community](https://support.marvelousdesigner.com/hc/en-us/community/posts/48277232788249-Collars)).
- **Interlining.** Stiffness comes from Bond, which makes an area drape "stiffer as if an interlining has been fused" ([Bond](https://support.marvelousdesigner.com/hc/en-us/articles/47358358998809-Bond)). CLO's preset list includes a 180 gsm hair-cloth undercollar reinforcement ([CLO Bond](https://support.clo3d.com/hc/en-us/articles/115000574207-Bond-How-to-Add-Interlining-Fusible-Reinforcement)), and MD's local preset cache includes "Fusible (Under Collar).fab" ([GUI research note](<../research_notes/Marvelous Designer MCP research/md_workflow_placement_layers.md>)).
- **Temporary strength.** Strengthen gives clean folds while the garment settles, and is then removed ([Strengthen](https://support.marvelousdesigner.com/hc/en-us/articles/47358253657497-Strengthen-Unstrengthen)).
- **Turned seams** sew double-layer pieces "crisp and flat" ([Sewing Line Type](https://support.marvelousdesigner.com/hc/en-us/articles/47358411103001-Sewing-Line-Type)).

A CLO lapel recipe combines all of these: fold and freeze the lapel, clone the facing as an internal shape, sew it with Turned seams, Superimpose Under and Bond ([CLO community](https://support.clo3d.com/hc/en-us/community/posts/360033634853-Sewing-Arranging-facing-for-lapel)). No bound name covers fold angle, Bond or Superimpose. So a model building a stand collar over the bridge gets its stiffness from fabric choice and its shape from the draft. A two-layer leather and satin collar stood unaided in the session ([session report](../../sessions/2026-10-11-vampire-cape.md)).

## A cape is an annular sector with a two-edge seam ledger

### Circle-fraction drafting gives every number a model needs

Capes come in two drafting families.

**Circle-fraction capes** are annular sectors. The inner radius is the neck measurement divided by 2π times the circle fraction, so a full circle uses C/2π, a half circle C/π and a quarter circle 2C/π ([The Shapes of Fabric](https://www.theshapesoffabric.com/2019/04/21/conquer-circle-skirt-patterns/)). Bucknell's SCA cloak checks out against the formula. It is a half circle with a 152 mm (6 in) neck radius and a 1524 mm length, and π × 152 mm gives a 479 mm neck edge ([Bucknell](https://eg.bucknell.edu/~lwittie/sca/garb/cloak.html)).

**Block-based capes** are traced from bodice or coat blocks and pivoted at the shoulder point. Pattern-Making.com's size-16 shoulder-dart cape is 1067 mm (42 in) long with a "minimum sweep" of only 1524 mm (60 in). Over the arm it adds a quarter of the across-back line as "ease allowance" ([Pattern-Making.com](https://pattern-making.com/drafts-hood-cape/)). Studio Faro gets a half circle that still fits the shoulder by setting the back block's centre back at right angles to the front block's centre front, with the shoulder points touching ([Studio Faro](https://www.studiofaro.com/drape-cape-top/)).

The table applies the circle rule to an illustrative 480 mm neckline and 1100 mm length. The figures are derived, not sourced.

| Cape | Fraction f | Neck radius r = N/(2πf) | Hem sweep 2πf(r + L) | Flat sector |
|---|---|---|---|---|
| Full circle | 1 | 76.4 mm | 7392 mm | 360° |
| Three-quarter | 0.75 | 101.9 mm | 5664 mm | 270° |
| Half circle | 0.5 | 152.8 mm | 3936 mm | 180° |
| Quarter circle | 0.25 | 305.6 mm | 2208 mm | 90° |

The user's reference is Maridah's Vampire Collar Capes. It is below the knee and lined, has a "bold standing collar", and marks 15.9 mm (5/8 in) seam allowances. Its piece list, and whether it is a circle or has shoulder seams, are only in the paid PDF ([Maridah](https://maridah.shop/products/vampire-collar-cape-set)). "Continuous over the shoulders" points to a circle-fraction body split only at centre back or centre front. That is an inference, to confirm with the user. DRCOS's vampire cape uses exactly four pieces: Body, Collar, Body lining and Collar lining ([DRCOS](https://dr-cos.info/fp-vampire.html)).

A collar's neck edge must equal the neckline's seam length, and the curve of that edge decides how the collar stands. The Creative Curator's mandarin collar shows the numbers involved ([The Creative Curator](https://www.thecreativecurator.com/draft-mandarin-collar-pattern/)):

- 90 mm from centre back to the shoulder and 105 mm from the shoulder to centre front, taken from the garment's own stitch line;
- the centre-front end raised 15 mm;
- a height of 35 mm;
- seam allowances of 5 mm on the collar edge and 10 mm on the neck edge.

A vampire collar runs the other way. Its standard form is "a semi-circular, fan-shape, cutting the interior curve the same length as the neckline", with a child's version about 203 mm (8 in) high (a search snippet of a [Threads forum](https://www.threadsmagazine.com/forum/adding-a-stand-up-collar-to-a-cape) thread). Mood's standing collar is 406 mm on the bottom edge and 457 mm on the top for a 381 mm neck ([Mood](https://blog.moodfabrics.com/?p=36768)). Real vampire collars stand because of heavyweight fusible interfacing ([Favecrafts](https://favecrafts.com/Halloween-Crafts/Rigid-Collar-Vampire-Cape-Sewing-Tutorial)).

Treating the collar as a cone, an inferred model rather than a sourced one, turns this into geometry a model can compute. A collar that leans out from vertical by α has inner radius R = N/(2π sin α) and a sector angle of 360° × sin α. At α = 30° that is a 180° half-annulus, the "semi-circular fan". For N = 480 mm and a height of 120 mm, α = 20° gives R = 223 mm, a 123° sector and a top edge of 738 mm. If the cape session's 38° flare is read as α, it was a 222° sector.

### Net shapes, notch-split edges and explicit ease are the simulator's rules

Home patterns use 15 mm seam allowances, industry around 10 mm, and enclosed seams 5–10 mm (search snippet via [Wikipedia](https://en.wikipedia.org/wiki/Seam_allowance)). A simulator, though, sews along the sewing line. CLO's DXF importer therefore swaps the cutting and sewing lines so that the allowance disappears during 3D assembly ([CLO community](https://support.clo3d.com/hc/en-us/community/posts/360037546313-Adding-Seam-Allowance-as-an-Internal-Line-Instead-of-External), search snippet). For md-mcp the rule is to **draft net shapes**.

MD's sewing tools show how unmatched lengths behave:

- Free Sewing shows a length difference in red once it exceeds one inch ([Free Sewing](https://support.marvelousdesigner.com/hc/en-us/articles/47358239854361-Free-Sewing-2D)).
- M:N sewing silently divides the N segments "in proportion to M segments" ([M:N Segment Sewing](https://support.marvelousdesigner.com/hc/en-us/articles/47358238742553-M-N-Segment-Sewing-2D)).
- Check Sewing Length highlights differences over 5 mm ([Check Sewing Length](https://support.marvelousdesigner.com/hc/en-us/articles/47358338510873-Check-Sewing-Length)).
- Crossed directional notches make MD reverse one piece ([Segment Sewing](https://support.marvelousdesigner.com/hc/en-us/articles/47358199517209-Segment-Sewing-2D)).

So every seam should be split at notches (centre back, shoulder points, centre front, collar ends, slit ends) into 1:1 pairs of equal length. Any intended ease should be stated explicitly, as when a straight hood edge is eased into the curved neck from the centre out ([Alley Cat Scratch](https://alleycatscratch.com/lotr/Things/FCloak/FCloak_pattern.htm)).

Jacket-style lining ease only applies when the lining hangs free at the hem: a hem 25 mm shorter and a 25 mm pleat at centre back ([Seamwork](https://seamwork.com/articles/a-lesson-in-lining)). Grain matters for drape. Half and three-quarter circles put centre front on the fold, which leaves the sides on the bias ([The Shapes of Fabric](https://www.theshapesoffabric.com/2019/04/21/conquer-circle-skirt-patterns/)). Real makers let circles hang 24 hours before levelling the hem ([WeAllSew](https://weallsew.com/how-to-hem-a-circle-skirt/)). The simulator's equivalent is to measure the hem after draping, rather than trusting the drafted radius.

Arm slits are at least 200–250 mm long ([Fairytale Cape](https://thisblogisnotforyou.com/make-the-cape-adding-armslits-to-your-cape/)). One way to make them is to leave a gap in a vertical seam and bind its edges (search snippet of [Threads](https://www.threadsmagazine.com/2011/06/20/how-to-sew-a-chic-cape)). That is also the cheapest form to simulate. Note that T-pose arms leave the body at shoulder height, so a slit placed for arms hanging down will not line up with them.

Cape constructions that were actually found bag the lining edge to edge. American Duchess sews the exterior shoulder seams and then the lining's, and stitches the whole perimeter except about 127 mm (5 in) at the back hem ([American Duchess](https://downloads.americanduchess.com/1910s-wrap-cape-pattern.pdf)). DRCOS sews the collar lining to the body lining and the shell collar to the shell body, then sews round the perimeter, leaving an opening at the hem ([DRCOS](https://dr-cos.info/fp-vampire.html)). Read together, they give a seam ledger in which every seam joins exactly two edges. This is inferred from both sources, and it is the plan the cape session lacked:

| Seam | Edges joined | Layers |
|---|---|---|
| Shell construction | Centre back, shoulder or panel seams | shell ↔ shell |
| Lining construction | The same list, sewn separately | lining ↔ lining, never to the shell |
| Shell collar to neckline | Collar neck edge ↔ back neck and each front neck, split at the shoulder notches | shell ↔ shell |
| Lining collar to neckline | The same split | lining ↔ lining |
| Collar edge | Shell collar top edge and centre-front ends ↔ lining collar | shell ↔ lining |
| Front edges | Left and right fronts, collar end to hem | shell ↔ lining |
| Hem | Every hem segment (left unsewn for a free-hanging lining) | shell ↔ lining |
| Arm slits | Both slit edges | shell ↔ lining |

The shoulder and panel lines, the body neckline and the interior of every piece stay unsewn between shell and lining. The layer clone sewed every one of those.

For common garments beyond capes, pattern makers start from blocks: bodice, sleeve, skirt and trousers. The drafting systems (Aldrich, Armstrong, Bunka and ESMOD) differ in ease and silhouette (search snippet of an [IJCST comparison](https://emerald.com/insight/content/doi/10.1108/IJCST-03-2021-0038)). FreeSewing offers open parametric blocks (Bella, Brian, Sarah "based on Aldrich", Titan) and one cloak, the Lunetius lacerna, but no cape ([FreeSewing](https://freesewing.eu/designs)). No machine-readable cape draft was found anywhere.

## Ten MD and CLO servers exist besides md-mcp, and none deletes a seam

A GitHub search for "marvelous designer mcp" returns four repositories, md-mcp among them ([GitHub search](https://api.github.com/search/repositories?q=marvelous+designer+mcp)). "clo3d mcp" returns eight ([GitHub search](https://api.github.com/search/repositories?q=clo3d+mcp)). The official MCP registry lists none of them ([MCP registry](https://registry.modelcontextprotocol.io/v0/servers?search=clo3d)). All are 2026 community projects with 0–37 stars. One practical catch: **`md-mcp` is already taken on PyPI** by an unrelated markdown server ([PyPI](https://pypi.org/project/md-mcp/)).

The closest relative is **Laboon2501/MarvelousDesigner-MCP**, verified by its author on MD 2026.0.315. It does five things md-mcp should note:

- **Listener.** It polls non-blocking sockets from a Windows `SetTimer` callback every 25 ms, so the plug-in's Run returns at once. The author measured menus staying usable and 100 read-only requests from four concurrent clients succeeding at about 125 ms median ([GUI_FREEZE_FIX.md](https://github.com/Laboon2501/MarvelousDesigner-MCP/blob/main/GUI_FREEZE_FIX.md)).
- **Seams.** It decodes `SeamLinePairGroupList` → `PairList` → `First`/`Second` with `ShapeID`, `Direction` and `LengthParam` into a sewing list ([agent_runtime.py](https://github.com/Laboon2501/MarvelousDesigner-MCP/blob/main/src/marvelous_designer_mcp/agent_runtime.py)). That is md-mcp's P1.1, already done against the same build.
- **Arrangement.** It calls `SetArrangementPosition` with three values after the piece index and checks the readback, but returns `world_transform=None` because "absolute 3D position/rotation API and units are not established" ([agent_runtime.py](https://github.com/Laboon2501/MarvelousDesigner-MCP/blob/main/src/marvelous_designer_mcp/agent_runtime.py)).
- **Timeouts.** Each mutation gets an operation ID. A timeout returns UNKNOWN, and reconciliation "never retries" ([repo](https://github.com/Laboon2501/MarvelousDesigner-MCP)).
- **No seam deletion.** Its skill says "restore_checkpoint and recreate is the fallback" ([SKILL.md](https://github.com/Laboon2501/MarvelousDesigner-MCP/blob/main/skill/marvelous-designer/SKILL.md)).

Its C++ plug-in "does not work in Marvelous Designer", because MD's loader scans only `.py` files ([cpp_plugin/README.md](https://github.com/Laboon2501/MarvelousDesigner-MCP/blob/main/cpp_plugin/README.md)). Glama scores its 42 tools 2 out of 5 on both disambiguation and tool count ([Glama](https://glama.ai/mcp/servers/Laboon2501/MarvelousDesigner-MCP)).

**ttiimmaacc/mcp-for-clo3d** solves the most, on CLO 2025.2 through a C++ DLL:

- **Seams.** `get_pattern_geometry` reports each seam's coverage of each line and pairs the seam's ends, so a twisted seam can be detected ([repo](https://github.com/ttiimmaacc/mcp-for-clo3d)).
- **Images.** `capture_3d` returns views to the model as MCP image content. It deliberately uses `ExportThumbnail3D`, because in CLO `ExportSnapshot3D` "opens CLO's snapshot dialog" ([server.py](https://github.com/ttiimmaacc/mcp-for-clo3d/blob/main/src/clo3d_mcp/server.py)).
- **Dialogs.** It is the only project that returns the host's own dialogs. It finds CLO's Qt message boxes by enumerating windows, then reads and clicks them through Windows UI Automation from the external Python process ([clo_ui.py](https://github.com/ttiimmaacc/mcp-for-clo3d/blob/main/src/clo3d_mcp/clo_ui.py)).
- **Limits.** It still lists "no free 3D move" and says editing or removing a seam is not possible ([repo](https://github.com/ttiimmaacc/mcp-for-clo3d)).

Two agent pipelines converge on drafting outside the host:

- **adriendelmas/pattern-making-skill** drafts blocks in a dependency-free `pattern.py` and checks seams after each step. It then sends one CLO line per pattern edge, so that seams are sewn by edge name: "The agent never computes coordinates in its head" ([repo](https://github.com/adriendelmas/pattern-making-skill)).
- **gigichengnc/clo-automation** states the principle outright: "Validate topology, not only counts" ([README](https://github.com/gigichengnc/clo-automation)).

The vendors' own AI features are hosted generators driven from the GUI: texture generators, an AI pose generator, and MD 2025.1's T-shirt-only Pattern Drafter. None of them is exposed through the API ([CG Channel](https://www.cgchannel.com/2025/08/clo-virtual-fashion-releases-marvelous-designer-2025-1/)). Style3D Studio V10.0 is the only vendor product that names "AI Auto Sewing", "AI Automatic Arrangement" and an MCP-powered workflow, and the MCP part covers print workflows only ([Textile Technology](https://www.textiletechnology.net/news/3d-software-automates-repetitive-tasks-and-links-design-workflows-219727)).

### Blender, Substance and Unity pair raw reach with curated verification

The mature servers for adjacent tools keep a raw escape hatch and add a small set of tools that see, measure, validate and recover:

- **Blender** (MCP for Blender). Its `look` returns the picture inline as MCP image content, 768 px by default, including one tiled sheet of named angles ([server.py](https://raw.githubusercontent.com/ahujasid/blender-mcp/main/src/blender_mcp/server.py)). Its maintainers moved code-correctness rules into the server instructions, arguing that "the errors are deterministic, so retries can't fix them", and added a test that keeps the instructions within a size budget ([PR #348](https://github.com/ahujasid/blender-mcp/pull/348)).
- **Substance Designer** (MikeLi-28). It drops raw code entirely. Its Graph Patch 1.0 resolves every reference before mutating anything, adds only, and rolls back what it created on failure. It reports a host version as "verified" separately from merely "capability_detected" ([architecture.md](https://github.com/MikeLi-28/Substance-3D-Designer-MCP/blob/main/docs/architecture.md)).
- **Unity** (CoplayDev). It shows 30 of its 50 tools by default and puts raw C# in an opt-in group, because "every visible tool adds tokens" ([tool groups](https://coplaydev.github.io/unity-mcp/guides/tool-groups)). Its open issues include an agent "often blocked by a 'Reload scene' popup", the same failure as MD's modal dialogs ([issues](https://github.com/CoplayDev/unity-mcp/issues)).
- **Unreal** (Epic's official server). It hides its toolsets behind three discovery meta-tools and runs "one at a time" on the game thread ([Epic docs](https://dev.epicgames.com/documentation/unreal-engine/unreal-mcp-in-unreal-editor)). That is independent support for md-mcp's `md_api` plus `md_call` design.

The evidence for guardrails is quantitative. In SWE-agent's ablations, removing the linter cut the resolve rate from 18.0% to 15.0%, and falling back to shell-only edits cut it to 10.3% ([arXiv](https://arxiv.org/html/2405.15793)). VIGA's render, inspect and revise loop reports a 35.32% improvement over one-shot generation on BlenderGym ([arXiv](https://arxiv.org/abs/2601.11109)). Server instructions raised workflow adherence from 12/20 to 17/20 runs in a small test ([MCP blog](https://blog.modelcontextprotocol.io/posts/2025-11-03-using-server-instructions/)), and tool-use examples raised accuracy on complex parameters from 72% to 90% ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)). Against that, Cloudflare argues that models write code to call tools better than they call tools directly ([Cloudflare](https://blog.cloudflare.com/code-mode/)). That supports keeping `run_md_python` for composing many calls. No published trial compares validate-then-apply against raw scripting inside a creative-app server, so the case for curated garment tools rests on convergent design and adjacent evidence.

Two constraints are concrete. **Claude Code truncates each server's instructions at 2,048 characters** ([Claude Code docs](https://code.claude.com/docs/en/mcp)), and md-mcp's instructions measure 1,987 characters in today's working tree ([server.py](../../../src/md_mcp/server.py)), leaving 61. And md-mcp sets no tool annotations. The spec's defaults then present every tool as destructive and non-idempotent ([MCP schema](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2025-11-25/schema.ts)).

## GarmentCode's stitch list is the seam plan md-mcp lacks

GarmentCode (pygarment) is the only parametric system whose output already has the shape md-mcp needs. It is MIT-licensed and installs with `pip install pygarment` ([GitHub](https://github.com/maria-korosteleva/GarmentCode)). Its specification JSON holds three things ([core.py](https://raw.githubusercontent.com/maria-korosteleva/GarmentCode/main/pygarment/pattern/core.py)):

- panels, as vertices and edges with optional curvature (quadratic, cubic or circular arc);
- a per-panel 3D `translation` and `rotation`;
- a **`stitches` list of (panel, edge) pairs**.

The older spec supports only "1-to-1 stitches" ([template spec](https://raw.githubusercontent.com/maria-korosteleva/Garment-Pattern-Generator/master/docs/template_spec_with_comments.json)). Its components include collars, lapels, a two-panel hood and circle skirts, but **no cape, cloak or lining** ([meta_garment.py](https://raw.githubusercontent.com/maria-korosteleva/GarmentCode/main/assets/garment_programs/meta_garment.py)). It has no DXF export and works in centimetres. Only its draping pipeline needs a manually built fork of NVIDIA Warp ([Installation.md](https://github.com/maria-korosteleva/GarmentCode/blob/main/docs/Installation.md)), and MD can do that job instead. A GarmentCode-to-MD converter is pure Python and therefore testable without MD. It maps panels to `PatternList` entries in millimetres and each edge to one MD line, with curves sampled into interior points. Each stitch becomes a `SeamLinePairGroup` with `LengthParam` fractions. That is an inference, but it rests on md-mcp's own measurement that pattern JSON expresses a seam as an arc-length span, so "the entire line-index failure class cannot be expressed" in it ([md-conventions](../../md-conventions.md)).

The learned systems mostly emit this same format, so one converter would serve all of them:

| System | Code and weights | Output | Notes |
|---|---|---|---|
| AIpparel | MIT code, weights on Hugging Face ([GitHub](https://github.com/georgeNakayama/AIpparel-Code)) | GarmentCodeData format (assumed; README silent) | Text or image to pattern |
| ChatGarment | Apache-2.0 code; no weights link found ([GitHub](https://github.com/biansy000/ChatGarment)) | GarmentCode parameters | GPT-4o rewrites prompts; valid seams by construction |
| Design2GarmentCode | Project page only ([GitHub](https://github.com/Style3D/design2garmentcode)) | GarmentCode programs | No code |
| DressCode/SewingGPT | Weights published; simulation needs Maya ([GitHub](https://github.com/IHe-KaiI/DressCode)) | Korosteleva 2021 format | Older, narrower dataset |
| GarmageNet | Claims only ([arXiv](https://arxiv.org/html/2504.01483v1)) | Multi-layer panels, point-wise sewing | Claims 99.16% sewing-point precision |
| NGL (2026) | Code "will be released" ([arXiv](https://arxiv.org/abs/2602.20700)) | Training-free VLM writes a DSL | Claims multi-layer outfits |
| Seam correspondence (2026) | No code ([arXiv](https://arxiv.org/abs/2607.21213)) | Seams inferred from 2D panels alone | Would fix seamless sources |

Every dataset found covers everyday garments. GarmentCodeData has 115,000 garments under CC BY 4.0 ([ETH Research Collection](https://www.research-collection.ethz.ch/entities/researchdata/d9df8fe3-2add-49a2-bb58-21750ca7970c)), and no source mentions capes, cloaks or linings in any of them ([GarmentCodeData](https://igl.ethz.ch/projects/GarmentCodeData/)). A cape is therefore out of distribution for every learned model. It is cheap to add to GarmentCode, though, as a circle-skirt-style panel hung from the neck.

The other routes are worse:

- **FreeSewing** draws good SVG pieces, but documents no seam pairing between parts ([FreeSewing snippets](https://freesewing.dev/reference/snippets)), and its GitHub repository was archived in April 2025 ([GitHub](https://github.com/freesewing/freesewing)).
- **Seamly2D** is GPLv3, and its moderators say its XML schemas "can and do change at any time" ([Seamly forum](https://forum.seamly.io/t/looking-for-official-documentation-or-xml-schema-for-sm2d-files/15403)).
- **DXF** fails twice over. MD staff say it cannot be imported (a search summary of an [MD community reply](https://support.marvelousdesigner.com/hc/ja/community/posts/48267712674585/comments/48267712824089)), md-mcp measured that no function takes the DXF option structs ([md-conventions](../../md-conventions.md)), and CLO users report that DXF export "will not save the sewn lines" ([CLO forum](https://support.clo3d.com/hc/es/community/posts/900003347303-How-to-export-a-DXF-AAMA-file-with-sewn-lines-information-included)).

The most attractive design needs no fine-tuned model at all. ChatGarment's model chooses a garment type and numbers, and a program draws the pattern. Claude can play that role directly by choosing GarmentCode parameters, and NGL is published evidence that the training-free form works. Placement is the part the converter cannot solve, because MD discards the JSON's arrangement offsets ([md-conventions](../../md-conventions.md)).

## What the research means for P0–P5 and the "nothing wrapped" rule

The research confirms the roadmap's diagnosis and changes its emphasis. P3's search for a transform has few routes left, and each of them is a measurement rather than a build. The work that would have prevented the cape session's failures is P1.1, P2.1 and P2.4, backed by P0.1, plus a drafting front end the roadmap does not yet name.

| Item | Research verdict | Proposed change |
|---|---|---|
| P0.0 listener outlives MD | A `SetTimer` listener has reportedly run on 2026.0.315 with a Run that returns at once | Prototype it before building Start/Stop menu entries. If it holds, there is no loop left to outlive MD's window, and bridge code stops running nested inside a script. Keep Start an explicit press. |
| P0.1 checkpoint | `.zprj` round trip measured intact; no seam removal anywhere | Make it the rollback for every seam-plan apply. Measure 3D-state fidelity. Adopt operation IDs with UNKNOWN on timeout, matching md-conventions' "a timeout abandons the reply, not the work". |
| P0.2 MD's errors | No log, no API; dialogs only | Re-scope from "find the log" to out-of-process enumeration of MD's top-level windows (ttiimmaacc's approach), plus state deltas. On a stall, reply "MD is showing a dialog: …" rather than timing out. |
| P0.3 images | Docs put the back at 8; peers return one tiled sheet at 640–768 px | Widen to 0–9 after re-measuring. Return front, back and side in one image, with piece and seam counts beside it. Try `ExportSnapshot2D` mode 1 for the board. |
| P0.4 write checks | Unchanged | Keep. |

On the open question, the evidence favours refining "nothing wrapped" into **"nothing hidden"**. `md_api`, `md_call` and `run_md_python` stay exactly as they are; every peer that has matured keeps a raw route, and code composes better than tool calls. Tools that read back, checkpoint, show, surface errors and validate wrap no MD behaviour; they check it. They belong in md-mcp beside `md_measure` and `md_snapshot`, because the cape session ran without the reliability skill, and a guardrail that lives only in a skill guards nothing when the skill is absent ([session report](../../sessions/2026-10-11-vampire-cape.md)). That cuts against AGENTS.md's placement of the seam-ledger validator in the skill. The resolution is to keep generic rules in md-mcp (duplicates, self-seams, reused intervals, length against stated ease) and garment-specific knowledge outside it: drafting formulas, the GarmentCode converter, the lining recipe and the placement procedure should live in the skill or a companion package that drives the bridge.

Keep the curated set small. Glama marked down a 42-tool MD server on disambiguation, and Blender went from 28 tools to 9.

## Conclusion

The cape session framed the problem as missing 3D placement, and the research reframes it. MD offers no transform, and neither does any CLO build or prior server. A garment that is drafted net, split at notches, planned seam by seam and sewn with deliberate linings needs far less placement, because sewing and gravity do the seating that Superimpose does in the GUI. The product md-mcp is missing is therefore not a better arrangement call but a trustworthy plan and a ledger to check it against. GarmentCode shows the plan can come from a program rather than from a model counting edges, and nobody has yet connected that format to MD.

The cheapest high-value step is a short session with MD open covering measurements 3, 4 and 5. They could overturn three documented claims at once: the view table, the arrangement-position no-op and the mandatory never-ending Run. The third would also reshape P0.0. md-mcp's measured notes are already the most detailed public record of how MD's API behaves, and that record is only as good as its next re-measurement.
